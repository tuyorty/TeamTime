# ADR 0003. Realtime: SSE поверх PostgreSQL LISTEN/NOTIFY

- Статус: принято
- Дата: 2026-10-26

## Контекст

Новое сообщение в чате должно появляться на сайте без перезагрузки. Данные идут в одну сторону: из бота в браузер. Пишут в базу два процесса, бот и API, поэтому одного in-memory брокера в API недостаточно.

## Решение

- Транспорт к браузеру — **Server-Sent Events** (`GET /api/v1/events`).
- Шина между процессами — **`LISTEN/NOTIFY` PostgreSQL** на канале `teamtime_events`. Тот, кто записал данные, делает `NOTIFY` в той же транзакции. Тогда событие уходит только после коммита.
- API держит одно `LISTEN`-соединение и раздаёт события по очередям подписчиков.
- Клиент на событие инвалидирует нужные запросы TanStack Query и показывает ненавязчивую подсветку.

## Почему не WebSocket

- Браузеру нечего отправлять обратно. Двунаправленный канал не нужен, а все правки идут обычными REST-запросами с CSRF-защитой cookie-сессии.
- SSE — обычный HTTP. Он проходит через nginx без upgrade-заголовков, сам переподключается и поддерживает `Last-Event-ID`.
- Меньше кода: ни протокола поверх сокета, ни heartbeat-логики на клиенте. Сервер шлёт комментарий-пинг раз в 15 с, чтобы прокси не рвали соединение.

## Почему не Redis

Лишний сервис в compose ради шины на десяток событий в час. `NOTIFY` транзакционен и уже есть.

## Последствия

- Payload `NOTIFY` ограничен 8000 байт. Поэтому шлём только тип события и идентификаторы, данные клиент перезапрашивает.
- Если события пропущены во время разрыва, клиент при переподключении инвалидирует всё. Это дешевле, чем журнал для `Last-Event-ID`.
