# Полная резервная копия фонда

Копия содержит PostgreSQL, чеки и вложения из БД, конфигурацию запуска и версию приложения.
Файлы шифруются AES-256-GCM до отправки. Ключ хранится отдельно от архива и отдельно от
обычного `.env`; без ключа восстановление невозможно. Telegram получает только шифротекст
и манифест контрольных сумм. Части ограничены 45 МиБ.

## Настройка на рабочем сервере

В обычном выпуске модуль фонда закрыт флагом разработки: его настройки и назначение
получателей через интерфейс недоступны. Новую настройку по шагам ниже выполняют только
в отдельной сборке разработки с включённым модулем. Пока используйте обычный `backup.sh`.
Если получатели были назначены раньше, полная копия продолжает использовать сохранённые
назначения независимо от отключения фонда. Установщик сам не запускает эту доставку и
не включает таймер. Перед включением таймера проверьте актуальность назначенных адресатов.

В «Финансы → Настройки фонда» назначить технического получателя копий. Руководитель и
технический получатель должны иметь подтверждённые привязки и начать личку с ботом.
Образы и скрипты должны быть одной версии.

Создание отдельного ключа без вывода в терминал (команда откажется перезаписать существующий):

```bash
cd /opt/xtime
sudo install -d -m 700 secrets
sudo python3 - <<'PY'
import base64
import os
from pathlib import Path
path = Path('/opt/xtime/secrets/backup.key')
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, 'wb') as out:
    out.write(base64.b64encode(os.urandom(32)))
PY
```

Сохранить ключ в независимом защищённом хранилище. Не добавлять его в репозиторий, сообщение
с архивом или сам архив. Затем выполнить первую копию и проверить получение обоими адресатами:

```bash
cd /opt/xtime
sudo ./backup-full.sh
sudo install -m 644 xtime-backup-full.service xtime-backup-full.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now xtime-backup-full.timer
systemctl list-timers xtime-backup-full.timer
```

Таймер запускает копию по воскресеньям в 04:00 Asia/Yekaterinburg. Для другого каталога
изменить `WorkingDirectory` и `ExecStart` в service до установки. Каждая неделя хранится
отдельно в `backups/full/`; автоматического удаления старых копий нет.

Если доставка завершилась таймаутом, повтор того же цикла не отправляет части повторно.
Состояние ошибки видно в «Состоянии системы» и `journalctl -u xtime-backup-full.service`.
Проверить, какие части действительно дошли. После проверки явный повтор с новым именем цикла:
`sudo XTIME_BACKUP_CYCLE=manual-2026-11-08 ./backup-full.sh`.
Это создаст новый архив и новые попытки доставки; не назначать такую команду циклически.

## Проверка восстановления на отдельной машине

Скопировать все `xtime-backup.partNNNN` и `manifest.json` в один каталог. Получить ключ
из отдельного хранилища. Использовать образ приложения версии из копии.
Следующая команда только проверяет и распаковывает архив; целевой каталог должен быть новым:

```bash
docker run --rm --user 0 --entrypoint teamtime \
  -v /srv/restore-check:/restore \
  -v /secure/backup.key:/run/secrets/backup.key:ro \
  xtime-backend:current \
  backup unpack /restore/encrypted /restore/unpacked /run/secrets/backup.key
```

Создать отдельный PostgreSQL и новую пустую БД. Не направлять восстановление на рабочий
контейнер. В следующем примере `xtime-restore-check-db` — имя специально созданного контейнера:

```bash
docker exec xtime-restore-check-db createdb -U restore xtime_restore
docker cp /srv/restore-check/unpacked/database.dump xtime-restore-check-db:/tmp/database.dump
docker exec xtime-restore-check-db pg_restore \
  -U restore -d xtime_restore --no-owner --no-acl --exit-on-error /tmp/database.dump
```

Подключить отдельный экземпляр API к восстановленной БД и проверить:

- версию миграций, участников, закрытые снимки и их отпечатки;
- остатки трёх корзин, обязательств, переплат и займов;
- доступность чеков и историю согласований;
- одинаковый расчёт в вебе и экспорте.

При проверке восстановления не запускать бот и доставку уведомлений. Использовать отдельный
порт сайта, пустой `BOT_TOKEN`, отключённые фоновые уведомления и не публиковать стенд наружу.
После успешной проверки отдельно согласовать переключение рабочего сервиса.

Формат проверяет порядок и контрольные суммы частей, аутентификацию каждого блока и явное
завершение потока. Подмена, усечение и неправильный ключ отклоняются до распаковки в
целевой каталог. Символические ссылки и выход за каталог назначения запрещены.

Сбой подготовки или доставки записывается в «Состояние системы» и вызывает одну
попытку личного уведомления ответственным за цикл. При недоступной БД, API или Telegram
доставить уведомление невозможно; журнал systemd остаётся источником диагностики.
Повтор запуска не дублирует уже предпринятую отправку.
